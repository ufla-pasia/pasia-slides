Spec-Driven Development e Programação Agêntica

PASIA - Aula T.10

Prof. Julio César Alves

DAC - ICET - Universidade Federal de Lavras

12/10/2026

Até agora, usamos IA para compreender código, projetar funções, escrever testes e desenvolver aplicações.

Hoje vamos discutir como organizar o desenvolvimento de um projeto com várias funcionalidades usando agentes de programação.

  • Como evitar que decisões importantes se percam ao longo das conversas?
  • Como conferir se o agente fez o que precisávamos, e não apenas algo que funciona?

Objetivos desta aula

Ao final, você deverá conseguir:

  • distinguir vibe coding de Spec-Driven Development (SDD);
  • reconhecer o papel das especificações, do agente e da revisão humana;
  • descrever um fluxo incremental de SDD, da constituição à validação;
  • identificar riscos, limites e aplicações de MCP, skills e subagentes.

Por que especificar?

Uma situação conhecida

Imagine que você pediu a um agente para criar um sistema de controle de tarefas.

  • Primeiro, pediu o cadastro de tarefas.
  • Depois, filtros por situação e por prioridade.
  • Em outra sessão, pediu exportação para CSV.

O agente pode implementar cada pedido, mas esquecer decisões anteriores ou modificar comportamentos já aprovados.

Vibe Coding vs. SDD

Vibe coding

  1. Pedimos algo.
  2. Observamos o resultado.
  3. Corrigimos pelo chat.
  4. Repetimos.

Spec-Driven Development

  1. Definimos objetivos e restrições.
  2. Registramos decisões em arquivos.
  3. Planejamos e implementamos.
  4. Validamos contra critérios explícitos.

Com vibe coding você torce para conseguir o que você precisa.

Já com SDD você chega mais perto do que realmente precisa.

  • Foca em dar contexto através de arquivos de especificação
  • Em vez de trabalhar diretamente com programação.

SDD não elimina a conversa: ela passa a produzir e manter decisões verificáveis.

SDD: Vantagens

  • Pode lidar com alterações grandes que afetam vários arquivos.
  • Lida com perda de contexto entre diferentes interações com agentes de IA.
    • Garante definições “não-negociáveis”.
  • Define objetivo, critérios de sucesso, restrições
    • Agente cria o plano completo.

Sistemas podem se tornar mais difíceis de manter

  • Quando várias pessoas usam diferentes IAs, com diferentes contextos para trabalhar no mesmo sistema.
  • Especificação é uma forma de fazer com que toda a equipe siga os mesmos critérios, padrões, na hora de fazer o sistema.

Em projetos novos, agentes podem gerar a especificação desde o início.

  • Mas podemos também criar especificações para projetos já existentes.

IA pode trabalhar por vários minutos desenvolvendo algo

  • E o resultado é muito melhor se gastarmos alguns minutos planejando melhor o que e como as coisas devem ser feitas.

Uma especificação é um contrato de trabalho

Ela esclarece:

  • O quê deve ser feito e por quê;
  • quais restrições devem ser respeitadas;
  • como reconhecer que a entrega foi concluída.

Especificação pode ser feita usando as próprias ferramentas de IA

  • Elas sumarizam as decisões principais de arquitetura.

Uma especificação é um contrato de trabalho

Servem como referência compartilhada entre pessoas, sessões e agentes diferentes.

  • Não garante código correto por si só.
  • Exige revisão e atualização contínuas.

Exemplo: requisito ambíguo

Crie uma lista de tarefas com prioridades.

O agente precisa decidir sozinho:

  • Quais prioridades existem?
  • Uma tarefa pode ficar sem prioridade?
  • Como aparecem as tarefas concluídas?
  • Os dados devem persistir entre execuções?

A mesma ideia, com critérios verificáveis

Exemplo de especificação

  • Cada tarefa tem descrição, prioridade (baixa, media, alta) e situação (pendente ou concluida).
  • A descrição não pode ser vazia.
  • Por padrão, a listagem mostra todas as tarefas.
  • O usuário pode filtrar por situação.
  • Para esta primeira versão, os dados ficam apenas em memória.

Teste de aceitação: ao marcar uma tarefa como concluída, o filtro pendente não pode mais apresentá-la.

Discussão

Atividade rápida

Um usuário diz: “O sistema precisa ser fácil de usar”.

  1. Por que esse requisito é difícil de validar?
  2. Reescrevam-no como um comportamento observável.
  3. Que teste permitiria verificar esse comportamento?

O que o humano delega — e o que não delega

Agentes podem analisar repositórios, editar arquivos, executar comandos e testes.

Pessoas continuam responsáveis por:

  • decidir objetivos e prioridades;
  • aprovar escolhas e restrições;
  • inspecionar resultados e riscos;
  • aceitar ou rejeitar a entrega.

O que o humano delega — e o que não delega

Enquanto o agente acelera a construção,

  • a especificação orienta a construção.

SDD: Benefícios

Controla o código com pequenas modificações na especificação.

  • Algumas linhas dizendo como deve ser o front-end pode gerar centenas de linhas de código.
  • Não precisamos gastar energia / tempo / raciocínio nos detalhes de implementação (abstração).

Elimina o decaimento de contexto

  • Acontece entre muitas sessões com agentes.
  • Especificações mantêm contextos não só entre sessões com o mesmo agente, mas também entre diferentes agentes.

SDD: Benefícios

Melhora a fidelidade à intenção

  • É mais provável que os agentes atendam seus objetivos.

Assim como compilador traduz código em binário.

  • Estamos agora traduzindo especificação em linguagem humana em código.

A ideia é trazer “engenharia” do ciclo de desenvolvimento de software para codificação com agentes.

Agente vs. Chat

Agente tem acesso ao código, ferramentas que você tem instaladas, etc.

Agentes são pair-programmers

  • Eles fornecem conhecimento técnico e velocidade.
  • Você, como arquiteto, apresenta o desenho da solução (blue-prints).
  • O agente é o músculo e a especificação é o cérebro.

Agente vs. Chat

A ideia é produzir software que não só funcione

  • mas que, principalmente, esteja alinhado com seus objetivos de longo prazo.

O ciclo de trabalho

Dois níveis de decisão

Alto nível: Constituição

  • Missão
  • Pilha tecnológica
  • Roadmap

Segundo nível: Funcionalidade — ciclo incremental

  • Requisitos
  • Planejamento
  • Validação
  • Implementação e revisão

Entre funcionalidades: replanejar quando as decisões mudarem.

Primeira fase: Constituição

Pode ser o que costuma ser feito em arquivo agents.md

  • Mas não depende de agente de IA específico.
  • E é mais estruturado.
  • Funciona como acordo entre os humanos e também com os agentes.

Precisamos focar no nível certo de detalhes:

  • E não naquilo que o agente pode descobrir sozinho.

Constituição: missão

A missão estabelece o contexto de longo prazo.

  • E define o por quê da solução.

Indica a visão e problema que queremos resolver;

  • público-alvo e principais necessidades;
  • escopo do produto e o que está fora dele;
  • objetivos e critérios gerais de sucesso.

Constituição: pilha tecnológica

Registra escolhas e restrições técnicas que precisam ser mantidas:

  • linguagem e bibliotecas permitidas;
  • modo de execução e distribuição;
  • persistência de dados;
  • organização arquitetural e convenções essenciais.

Indica como a solução se encaixa na pilha de tecnologia da empresa.

  • Evita que cada agente reinvente a arquitetura do projeto.

Constituição: roadmap

Lista com fases de implementação ordenadas.

  • Cada fase terá seu próprio arquivo de especificação.

É um documento vivo: novas informações podem mudar sua ordem ou granularidade.

Segunda fase: Funcionalidade

Terminada a constituição entramos no processo de criar funcionalidades.

Para cada funcionalidade, o processo envolve

  1. Especificação
  2. Implementação
  3. Validação

Terceira fase: Replanejamento

É executada entre uma fase de funcionalidade e outra

  • Melhora a definição da Constituição
  • Melhora o próprio processo.

Esse ciclo Funcionalidade -> Replanejamento -> Funcionalidade é repetido até terminarmos a solução.

Programação Agêntica

Devemos lembrar do nível correto de detalhamento.

  • Nós somos os arquitetos que passamos os projetos para os construtores

Nosso papel é:

  • Projetar
  • Supervisonar
  • Revisar
  • Aceitar… ou pedir mudanças.

Nosso foco deve ser em fornecer contexto para os construtores fazerem o trabalho deles.

  • Assumindo que eles sabem fazer o trabalho deles.

Por que trabalhar em etapas?

Mudanças pequenas:

  • tornam diffs mais fáceis de revisar;
  • permitem localizar regressões;
  • reduzem o custo de refazer escolhas equivocadas;
  • diminuem a quantidade de contexto necessária para a próxima etapa.

Implementar “tudo de uma vez” pode funcionar, mas aumenta o volume de código a verificar.

Exemplo de estrutura

projeto/
├── README.md
├── specs/
│   ├── missao.md
│   ├── pilha-tecnologia.md
│   ├── roadmap.md
│   └── 01-cadastro-tarefas/
│       ├── requisitos.md
│       ├── planejamento.md
│       └── validacao.md
├── src/
└── tests/

Os nomes e diretórios são convenções do nosso exemplo, não exigências do SDD.

Ambiente

SDD é agnóstico em relação às ferramentas utilizadas.

  • Pode ser qualquer IDE.
  • Qualquer agente de IA.
  • É altamente recomendável usar controle de versão (git) para a revisão das alterações feitas pelo agente de IA.

Criando a Constituição

Lembre-se que constituição se refere ao planejamento de alto nível sobre o que será desenvolvido agora (e até no futuro).

  1. Missão: ideia principal.
  2. Pilha de Tecnologia: como ela se encaixa na pilha da empresa.
  • Precisamos, principalmente, limitar o que será usado.
  1. Roadmap: quais funcionalidades são planejadas.

Usamos o próprio agente de IA para nos ajudar a escrever a constituição.

Passo 1: Descrição do projeto README.md

Colocar a descrição em alto nível do projeto.

  • Focar especialmente no que se espera com a solução a ser desenvolvida.
  • Consideranto tanto o público-alvo (usuários finais).
  • Quanto o público interno (desenvolvedores / mantenedores da solução).

Passo 2: Criação das especificações da constituição

Pode ser feita conversando-se com o agente.

Exemplo de Prompt

Estamos criando XX, que é um XXXX. Veja no arquivo README.md o que é esperado no projeto. Vamos criar uma “constituição” em um diretório specs:

  • missao.md
  • pilha-tecnologia.md
  • roadmap.md para organizar a implementação em alto nível, em passos bem pequenos.

SDD funciona melhor com abordagem human in the loop.

  • Quando revisamos / validamos pequenas modificações.

Revise o que foi criado pelo agente.

  • Se precisar melhorar alguma coisa na especificação peça o agente, em vez de mudar manualmente.
  • Isso evita que algum documento relacionado fique desatualizado.

Passo 3: comitar os arquivos

É importante usar controle de versão, comitar os arquivos.

  • Isso permite ter rastreabilidade / histórico das decisões relacionadas à especificação.

Especificando a Funcionalidade

Importante: Comece uma nova sessão com o agente, pois todo o contexto que ele precisa está na especificação.

Exemplo de Prompt

Encontre a próxima fase em specs/roadmap.md, crie uma branch e me pergunte sobre a especificação da funcionalidade. Crie:

  • Uma nova pasta YYYY-MM-DD-nome-funcionalidade dentro de specs para essa funcionalidade.
  • Dentro dela:
    • planejamento.md com uma série de grupos de tarefas numerados.
    • requisitos.md para escopo, decisões e contexto.
    • validacao.md para como saber se a implementação foi feita com sucesso e pode ser incluída (merge).

Use specs/missao.md e specs/pilha-tecnologia.md para se guiar.

Na conversa com o agente revise com cuidado e responda às perguntas feitas.

  • Você não tem que aceitar tudo que o agente está propondo.
  • É importante fazer escolhas conscientes e que guiem para o que realmente é necessário.

Quando a especificação for gerada, revise-a com cuidado.

  • É muito importante que ela comece correta para que o trabalho fique bem feito.
  • Se alguma coisa não estiver certa, peça ao agente para corrigir.

Comece revisando planejamento.md.

  • Veja se tem tudo que é necessário.
  • Se faltar algo peça ao agente para adicionar (ex: um novo grupo de tarefas para algo que faltou).

Depois revise requisitos.md.

  • Não passe direto nisso, mas também não é para ficar entrando em detalhes técnicos (ex.: nomes de variáveis).
  • Queremos controlar o processo, mas não controlar demais o agente.

Por fim, revise validacao.md.

  • É importante que o que esteja sendo proposto realmente teste se tudo funciona como deveria.

Lembre-se que o que está escrito em algumas linhas nos arquivos markdown, pode gerar centenas de linhas de código.

  • Então o tempo gasto revisando o texto, é tempo muito bem investido!

Implementação da Funcionalidade

Comece uma nova sessão com o agente.

Diga ao agente para fazer a implementação da funcionalidade.

  • Você pode pedir para ele implementar todas as funcionalidades restantes
  • Ou fazer um grupo de tarefas de cada vez
    • É bem útil quando uma mudança pode ter grandes implicações depois.

Revise as alterações feitas.

  • Em seguida, execute a aplicação (se for o caso).

O agente fez as validações dele, no próximo passo, faremos as nossas.

Validação da Funcionalidade

Avalie o código criado

  • Foco no alto nível: se a implementação funciona e atende aos requisitos
  • E não em detalhes: como quais classes foram criadas.

Se precisar alterar algo, peça ao agente para atualizar não só implementação, mas também o planejamento.

  • Exemplo: Atualizespecs/YYYY-MM-DD-nome-funcionalidade.mde a implementação para que ...

Antes de terminar funcionalidade, pergunte-se:

  • Os critérios de aceitação foram atendidos?
  • Os documentos refletem o comportamento real?
  • Há testes relevantes e o código está versionado?
  • O roadmap representa o que ainda falta fazer?

Esse processo é o que chamamos de human in the loop.

  • Atuamos na revisão e não na programação em si.
  • Agentes são muito rápidos para programar, mas nós temos que guiar para que seja feito o que realmente precisamos.
  • Removemos a sobrecarga mental de ter que escrever, evoluir e validar cada linha de código.
    • Tendo a especificação, o próprio agente valida o que está fazendo.

Podemos até fazer alterações diretamente no código, quando isso parecer ser mais eficiente.

  • Mas lembre-se de pedir o agente para atualizar a especificação, para refletir o que foi feito.

Ao terminar a validação marque o trabalho como completo.

Exemplos de prompts úteis para finalização

Exemplo de Prompt

Faça um PR para a branch develop para a fase que implementamos, marcando-a como finalizada em specs/roadmap.md

Exemplo de Prompt

Marque esta fase em specs/roadmap.md como completa, comite o que foi feito, mude para main, faça o merge dessa branch e delete-a.

Replanejamento

Antes de prosseguir para a próxima funcionalidade, vale a pena refletir sobre o processo.

  • Às vezes precisamos ir mais devagar para que, no final, sejamos mais rápidos.

Se for necessário alterar a constituição do projeto, é recomendável fazer isso em uma branch específica.

  • Isso ajuda a identificar qual versão da constituição gerou qual código.
  • Pode ser identificado que seria necessário seguir um design responsivo, por exemplo.

Se a implementação do que está sendo alterado for pequena, pode ser que faça sentido fazer na própria branch de replanejamento.

  • Mas se for algo maior, vale a pena acrescentar como uma fase futura do Roadmap.

Queremos que a especificação guarde as decisões, não apenas o código.

  • E precisamos que as duas coisas estejam sincronizadas.
  • Portanto, é necessário deixar isso claro para o agente.

Princípio: especificação e código devem evoluir juntos.

Precisamos manter alterações pequenas.

  • Facilita a revisão da especificação e do código que precisamos fazer.

No replanejamento, é interessante verificar se os próximos passos ainda fazem sentido.

  • Pode ser necessário alterá-los, mudar a ordem, combinar várias fases em uma só ou separar em mais de uma.

A fase de replanejamento pode ser usada também para sincronizar stakeholders do projeto que não sejam de perfil técnico.

  • Um exemplo para facilitar isso seria manter um log das mudanças (change log).
  • Podemos usar skills para isso.

Próxima fase de funcionalidade

É muito importante evitar a fadiga de IA.

  • IA gera muito código, que pode ser bem complicado de revisar.
  • Precisamos garantir que, na nova fase de funcionalidade, a IA siga a especificação, e não alguma memória das últimas conversas que tivemos.
  • Além de ajudar a evitar custos desnecessários com grande histórico de contexto.

Por isso, é importante verificar:

  • Terminamos realmente o que estávamos fazendo?
  • Já foi feito merge da última funcionalidade ou replanejamento?
  • A próxima fase está clara e bem definida?

E então limpamos o contexto do agente.

  • Para começarmos a próxima fase.

Podemos começar com o mesmo prompt da primeira funcionalidade.

  • E, se isso for repetitivo, podemos automatizar nosso workflow.

E então seguimos os mesmos passos da funcionalidade anterior.

  • Ter fases de replanejamento entre funcionalidades ajuda a evitar transbordamento de contexto.
    • Não só do agente de IA, mas nosso também.

Às vezes precisamos pedir ao agente comece implementando apenas parte da funcionalidade.

  • Para manter o trabalho gerenciável.

Dica: observar o “raciocínio” do agente pode ser útil para entender melhor suas decisões.

Durante o desenvolvimento, você pode descobrir que algum padrão de codificação deveria estar sendo seguido, mas não tinha sido especificado.

  • Tudo bem, a ideia é evoluir a especificação também ao longo do projeto.

Usar o depurador para rodar testes automatizados pode ser uma boa estratégia para ganhar mais entendimento sobre como funciona o código.

Podemos também pedir o agente para fazer uma revisão profunda das alterações de uma branch antes de prosseguir.

Exemplo de Prompt

Faça uma revisão profunda: dispare múltiplos subagentes para verificar todas as alterações dessa branch a partir de três perspectivas diferentes e verifique se alguma coisa não faz sentido, poderia ser melhor, etc.

Criar subagentes é interessante porque não polui a janela de contexto do agente principal.

  • E dá a oportunidade para a IA avaliar melhor o código.
  • Os subagentes podem retornar problemas e sugestões de melhoria no projeto, que você pode decidir tratar ou não.

Projetos Legados

SDD pode ser útil também para projetos já existentes, criados sem IA.

Devemos começar criando a constituição do projeto.

  • Podemos usar basicamente o mesmo prompt que usamos para o projeto novo.
    • Mas listando os artefatos que podem ser usados para entender o projeto: como código, README, lista de TODOs, issues, etc.
  • A IA usará Engenharia Reversa para gerar a especificação a partir do projeto existente.

A constituição criada permitirá que futuras funcionalidades desenvolvidas pelo agente de IA estejam alinhadas com o que foi desenvolvido antes no projeto.

  • Lembre-se que a especificação deve ser versionada assim como o código.
  • Depois de criada a constituição, o processo SDD é exatamente o mesmo feito para novos projetos.

Comentários sobre Experiência sobre uso real de SDD

App Web usando Python Streamlit

Eu já tinha os requisitos do ponto de vista do usuário.

  • Criei a missão usando esse arquivo como um TODO de demandas.
  • E escrevi um README com necessidades gerais do projeto.
  • Gerei também um arquivo ui-spec.md usando gemini a partir de prints e prototipação feita com Excalidraw.
  • Usei VS Code + Copilot + Git.

Fase inicial do processo até relatórios de finos funcionou bem.

  • Apesar do consumo de tokens ser alto.
  • Copilot a princípio usando GPT 5.3 Codex.
    • Depois passou a usar MAI-Code-1-Flash.

Entre uma fase e outra eu pedia para atualizar a ui-spec.md.

  • Porque fui descobrindo que ele não representava exatamente o que eu tinha na prototipação inicial.

Mas ao chegar na parte de Fretes o resultado começou a ficar bem ruim.

  • Não fazia o que eu queria
  • Atrapalhava o que já estava pronto de finos.
  • Tentei ir acertando com o prompt mas vi que nunca ficava certo.
  • Pode ser que aí tenha começado a fazer falta o conhecimento técnico mais profundo sobre Streamlit.
  • Mas desconfiei do modelo MAI.

Experimentei simplesmente descartar a implementação e começar uma nova sessão escolhendo modelo Claude Sonnet 5.

  • Ele faz coisas bem mais profundas, pensa mais, e até fez testes usando a própria aplicação web gerada.
  • Mas demora bastante, faz muita coisa e consome muitos tokens!
  • E o resultado do primeiro grupo implementado já não foi legal.

Resolvi então tentar

  • Forçar novamente o uso do Codex no Copilot.
  • Refinar o planejamento
    • Fiz um prompt relatando as dificuldades que eu estava encontrando.
    • Os arquivos de planejamento, requisitos e validação foram atualizados.

Mas aí notei uma possível fonte do problema.

  • O arquivo ui-spec.md talvez estivesse atrapalhando.
  • Quando fiz mudanças durante a implementação dos relatórios de finos usei a IA para atualizá-lo, mas sem mexer nas funcionalidades futuras.
    • Elas acabaram ficando com definições desatualizadas.
  • Usei então a IA para atualizar isso tanto para Fretes como para a fase futura de Prêmios.

Fiz então a implementação:

  • E enfim funcionou!
  • Com um bom consumo de tokens, mas foi rápido.
  • Observação: agente cria “memória” interna que pode influenciar no resultado (não sei exatamente como o copilot trata isso entre modelos diferentes).

Regressões

Ao longo do desenvolvimento notei que algumas decisões acabavam sendo perdidas, e a implementação “voltava” para algo que eu não queria.

  • Ex.: quando usuário não tinha permissão eu queria que os botões de Download simplesmente não aparecessem.
  • Mas na primeira implementação ficavam desabilitados com uma mensagem dizendo que usuário não tinha acesso.
  • Eu então pedi para ficar do jeito que eu queria. Mas, mais adiante, ao tratar os fretes, essa decisão voltou.
  • Provavelmente porque isso não estava claro na especificação do Roadmap.

No minicurso que fiz, depois do planejamento da funcionalidade partia-se diretamente para implementação.

  • Mas usando o Codex, ele sempre sugeria criar um checklist de implementação técnica por arquivo antes da implementação, mas eu não fiz nenhuma vez.
  • Teria sido melhor? :)

Replanejamento

Fiz um replanejamento para os relatórios sob demanda.

  • Ver prompt.
  • Replanejamento foi importante e teve bom resultado.

Situações inesperadas

Após o replanejamento o agente mockou os dados diretamente na main_view.

  • Sem seguir contrato de divisão de camadas que era algo crítico da arquitetura.

Briga para fazer notificação funcionar

  • Problema da implementação minha?
  • Realmente não é tão simples no Streamlit?

O consutmo de tokens é bem alto

  • No meu caso compensou, pois eu gastaria muito mais tempo para o desenvolvimento.
  • E esse tempo economizado eu estaria desenvolvendo outras coisas, portanto, ganhei produtividade.
  • Mas essa conta é complexa:
    • Provavelmente eu teria gastado menos se tivesse mais conhecimento técnico sobre Streamlit.
    • E se usasse outra IA (como ChatGPT, Gemini para discutir decisões antes de aplicar no Copilot).

Testes automatizados

Provavelmente eu não teria implementado tantos testes automatizados.

  • O que na verdade seria um deficiência da minha implementação
  • Portanto, o resultado com IA, nesse ponto, foi melhor.

Padrões usados em Programação Agêntica

Como a evolução rápida dos agentes de IA,

  • não é recomendado que nosso SDD esteja fortemente vinculado a um agente específico.

Por isso é importante usar padrões que nos ajudem a manter o trabalho funcionando

  • mesmo que precisemos usar outro agente de IA no futuro.

Exemplos de padrões

  • MCP
  • Agents.md
  • Skills

MCP

Model Context Protocol é um padrão de código-aberto para conectar agentes de IA com ferramentas externas.

  • Permite que agente tenha acesso, por exemplo, a banco de dados, APIs, sistemas de acesso restrito, etc.
  • Existe MCP para acessar, por exemplo, versão mais atualizada de pacotes.

Existem vários MCPs úteis para o que precisamos.

AGENTS.md

AGENTS.md pode reunir instruções recorrentes para agentes que trabalham no repositório.

  • É uma espécie de README, mas para os agentes.

Skills

Podemos criar skills que facilitem nosso trabalho evitando tarefas repetitivas.

  • O prompt para especificar a funcionalidade, por exemplo, é repetitivo.
    • Ou para atualizar o changelog do projeto, para tarefas de validação e qualidade de código.
  • Podemos usar o próprio agente de IA para criar as skills.

Exemplo de Prompt

Quero parar de ficar repetindo o prompt de especificação. Use seu criador de skill para me ajudar a escrever uma especificação de funcionalidade, como uma skill local. Segue o prompt que tenho usado: …

Skills

Assistir a saída do agente enquanto cria a skill pode ajudar a verificar se ela está sendo criada como gostaria.

  • Para usar uma skill, podemos dizer diretamente para usá-la ao fazer uma tarefa

Exemplo de Prompt

Use a skill de especificação de funcionalidade para especificar a próxima …

Plugins

São extensões para agentes de IA que podem ser instaladas e atualizadas.

  • Geralmente são específicas para cada agente de IA.

Subagentes e inspeção independente

Algumas ferramentas permitem delegar revisões a agentes auxiliares.

  • Um revisa requisitos.
  • Outro procura falhas de teste.
  • Outro verifica arquitetura e manutenção.

Revisões independentes ajudam, mas não substituem a verificação humana e podem aumentar o consumo de tokens.

Spec-kit e OpenSpec

github.com/spec-kit é uma tentativa de formalizar fluxo de trabalho com SDD.

  • Fornece comandos para agentes de IA que fazem o que nós vimos.

OpenSpec é uma alternativa.

  • github.com/fission-ai/open-spec

Backlog

Às vezes, durante o desenvolvimento de uma funcionalidade temos uma ideia de algo que poderia ser feito.

  • Como mudar a banco de dados usado, por exemplo.
  • E conversamos sobre isso com o agente, mas não queremos implementar agora.

Podemos pedir o agente para criar uma pasta de backlog e salvar essa conversa (com recomendações) de forma organizada (por data e assunto, por exemplo).

  • De forma que depois possam ser consultadas para serem incluídas no Roadmap.

Checkpoint — o que está errado?

“O agente criou testes e todos passaram. Portanto, podemos fazer o merge sem conferir requisitos.”

Discuta: que tipos de falhas esse raciocínio pode esconder?

  • Critérios de aceitação mal compreendidos.
  • Testes insuficientes ou alinhados a uma implementação errada.
  • Violação de restrições técnicas não exercitadas pelos testes.
